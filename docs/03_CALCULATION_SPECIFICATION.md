# Calculation Specification

## 1. Purpose and authority

This document defines the calculation behavior that implementations and tests must follow. UI labels may be simplified, but authoritative values must be generated by the domain engine. Any future change to a formula, scheduling convention, or rounding rule requires a versioned decision, migration impact review, and new reference tests.

## 2. General numerical rules

- Store durations and working time in an integer base unit, preferably minutes.
- Store money and quantities using decimal arithmetic rather than binary floating point where exact reconciliation matters.
- Store percentages internally as decimal fractions, for example `0.25` for 25%.
- Do not round intermediate calculations unless a standard explicitly requires it.
- Round only at presentation or defined posting boundaries.
- Every report must disclose display precision and currency.
- Division by zero, missing inputs, or undefined ratios produce `null/not available` plus a reason, never silent zero.
- Calculation results must include warnings and provenance.

## 3. Scheduling terminology

For activity `i`:

- `D_i`: remaining or planned working duration
- `ES_i`: early start
- `EF_i`: early finish
- `LS_i`: late start
- `LF_i`: late finish
- `TF_i`: total float
- `FF_i`: free float
- `Cal_i`: activity calendar

Dates are working-time instants. Calendar functions must support:

- `addWork(date, duration, calendar)`
- `subtractWork(date, duration, calendar)`
- `workDifference(start, finish, calendar)`
- `nextWorkInstant(date, calendar)`
- `previousWorkInstant(date, calendar)`

The engine must define inclusive/exclusive date display consistently. Internally, intervals should be half-open `[start, finish)` to avoid one-day ambiguity.

## 4. Relationship constraints

For predecessor `p`, successor `s`, and lag `L`, relationship constraints are evaluated in working time using a documented lag calendar. The recommended initial rule is to use the successor calendar for FS and SS lag placement and the predecessor calendar for FF and SF only if tests confirm intuitive behavior; alternatively use an explicit relationship calendar. The selected rule must be fixed in an ADR before implementation.

Conceptual constraints:

- **FS:** `ES_s ≥ addWork(EF_p, L)`
- **SS:** `ES_s ≥ addWork(ES_p, L)`
- **FF:** `EF_s ≥ addWork(EF_p, L)`
- **SF:** `EF_s ≥ addWork(ES_p, L)`

To convert finish constraints into a start candidate:

- For FF: `candidate ES_s = subtractWork(required EF_s, D_s)`
- For SF: `candidate ES_s = subtractWork(required EF_s, D_s)`

Milestones have zero duration but must still snap to valid working instants under their calendar.

## 5. Forward pass

### 5.1 Initial condition

The project start is an explicit project start milestone or configured project start datetime. Root activities without predecessors start no earlier than the project start, applicable constraints, and status-date rules.

### 5.2 Candidate early dates

For each activity in topological order:

1. Gather all relationship-derived start/finish requirements.
2. Apply actual start/finish and status-date rules.
3. Apply soft and hard constraints.
4. Select the maximum controlling requirement for the relevant boundary.
5. Snap to valid working time.
6. Calculate the opposite boundary using the activity calendar and remaining duration.
7. Record the driving relationship or constraint.

For a simple unstarted activity without finish-driving relationships:

`ES_i = max(project start, predecessor requirements, start constraint)`

`EF_i = addWork(ES_i, D_i, Cal_i)`

When finish relationships drive the activity, compute the required finish and derive start by subtracting duration, then compare against start-driving requirements. If both cannot be satisfied, the later start governs and the result must identify the non-driving relationship slack.

### 5.3 Actualized activities

- Completed activity: actual start and actual finish are authoritative; remaining duration is zero.
- In-progress activity: actual start is fixed; remaining work is scheduled from the status date according to the selected out-of-sequence rule.
- Unstarted activity: early start cannot occur before the status date unless the selected update convention permits historical planned dates solely for variance display.

The engine must keep baseline/planned dates separate from current forecast dates.

## 6. Backward pass

### 6.1 Completion anchor

The backward pass begins from:

1. an explicit required project finish, if configured; otherwise
2. the calculated finish of the project finish milestone; otherwise
3. the latest early finish among terminal activities, with an open-end warning.

### 6.2 Late dates

Process activities in reverse topological order. Relationship constraints conceptually impose:

- FS: `LF_p ≤ subtractWork(LS_s, L)`
- SS: `LS_p ≤ subtractWork(LS_s, L)`
- FF: `LF_p ≤ subtractWork(LF_s, L)`
- SF: `LS_p ≤ subtractWork(LF_s, L)`

The earliest permissible late boundary among successors controls. Convert between late start and late finish using the predecessor activity duration and calendar.

Hard date constraints may create negative float and must not be silently absorbed.

## 7. Float and criticality

### 7.1 Total float

Recommended definition:

`TF_i = workDifference(ES_i, LS_i, Cal_i)`

It should equal the working-time difference between early and late finish within tolerance. Any discrepancy indicates calendar conversion or rounding issues and must be tested.

### 7.2 Free float

Free float is the amount an activity can be delayed without delaying the early date of any immediate successor. It must be calculated relationship-by-relationship and the minimum applicable slack governs.

For a simple FS relationship:

`FF_(p,s) = workDifference(EF_p + lag, ES_s, relationship calendar)`

Equivalent formulas are required for SS, FF, and SF. Terminal activity free float is zero unless an explicit project-finish target provides available slack.

### 7.3 Critical and near-critical

- Critical by default: `TF ≤ 0` working minutes.
- Near-critical: `0 < TF ≤ user threshold`.
- Negative float: `TF < 0`, displayed separately as schedule infeasibility against a required date or constraint.

Critical-path tracing must follow driving relationships and not rely only on activity color.

## 8. Constraints

### 8.1 Soft constraints

Start-no-earlier-than and finish-no-earlier-than affect the forward pass. Start-no-later-than and finish-no-later-than affect the backward pass and may create negative float.

### 8.2 Hard constraints

Must-start-on and must-finish-on force dates and can break natural logic. They require a prominent warning, reason field, and report disclosure.

### 8.3 Deadlines

A deadline does not move dates. It calculates deadline variance and flags forecast finish later than the deadline.

## 9. Baseline and progress calculations

### 9.1 Baseline values

A baseline is an immutable snapshot of approved schedule and cost data. It includes at least baseline ES/EF/LS/LF, duration, quantity, budget, and time-phased values.

### 9.2 Duration percent complete

For a started activity with original duration `OD` and remaining duration `RD`:

`Duration % = max(0, min(1, (OD - RD) / OD))`

This method must not be used when `OD = 0`.

### 9.3 Physical percent complete

Physical progress is manually entered or derived from weighted steps. It must be independent of elapsed duration.

### 9.4 Units percent complete

For planned quantity `Q_plan` and accepted installed quantity `Q_done`:

`Units % = Q_done / Q_plan`

Handle zero or negative planned quantity as invalid unless the item is explicitly non-measurable.

### 9.5 Weighted milestones

For milestones `j` with weights `w_j` that sum to 1 and completion `c_j` in `[0,1]`:

`Physical % = Σ(w_j × c_j)`

Weights must reconcile to 100% within tolerance.

## 10. PERT

For optimistic `O`, most likely `M`, and pessimistic `P` durations:

`Expected duration, t_e = (O + 4M + P) / 6`

`Standard deviation, σ = (P - O) / 6`

`Variance, σ² = ((P - O) / 6)²`

Validation requires non-negative estimates and normally `O ≤ M ≤ P`.

For a path with independent activity durations:

`Path mean μ = Σ t_e`

`Path variance = Σ σ²`

`Path standard deviation = sqrt(Σ σ²)`

For target duration `T`:

`Z = (T - μ) / σ_path`

Approximate completion probability:

`Pr(completion ≤ T) = Φ(Z)`

The interface must disclose that this approximation may be inaccurate when paths can switch, activities are correlated, distributions are not well approximated by the assumed model, or a single critical path is not stable.

## 11. BOQ and estimating

### 11.1 Basic amount

`Base amount = Quantity × Base unit rate`

If waste is applied to quantity:

`Adjusted quantity = Quantity × (1 + Waste factor)`

`Direct amount = Adjusted quantity × Base unit rate`

If waste is embedded in resource consumption instead, it must not be applied again at item level.

### 11.2 Unit-price analysis

For resource component `r`:

`Component unit cost_r = Consumption coefficient_r × Resource rate_r`

`Direct unit cost = Σ Component unit cost_r`

`Direct item amount = Quantity × Direct unit cost`

### 11.3 Markup waterfall

Markup layers must define their basis. Example:

1. Direct cost
2. Site overhead as percentage of direct cost
3. Subtotal A
4. Home-office overhead as percentage of Subtotal A
5. Subtotal B
6. Contingency as percentage of selected basis
7. Profit as percentage of selected basis
8. Tax as percentage of taxable subtotal

The engine must not assume all percentages share the same base. Each layer stores `basis`, `rate`, `fixed amount`, `sequence`, and `rounding rule`.

### 11.4 Allocation to activities

For BOQ amount `B` and allocation weights `a_i`:

`Activity budget_i = B × a_i`

`Σ a_i = 1` within tolerance. Unallocated balance must remain visible and excluded or included according to report settings.

## 12. Time phasing and S-curves

### 12.1 Distribution domain

Values are distributed only across working periods unless the selected curve explicitly uses elapsed calendar time. The chosen basis must be stored.

For activity total value `V` and period weights `w_k`:

`Incremental value_k = V × w_k`

`Σ w_k = 1`

`Cumulative value_n = Σ(k=1..n) Incremental value_k`

The final cumulative value must reconcile to `V` after controlled residual adjustment. A recommended rule is to place the minor rounding residual in the final non-zero period.

### 12.2 Standard distributions

- Uniform: equal weight per working time unit
- Front-loaded: decreasing weights over time
- Back-loaded: increasing weights over time
- Bell-shaped: normalized symmetric or configurable beta-like weights
- Custom: user-entered weights normalized only after explicit confirmation
- Milestone: value posted at defined completion points

Distribution parameters must be versioned so regenerated curves remain reproducible.

### 12.3 Early and late curves

Early curve uses early dates. Late curve uses late dates. Both use the same total values and distribution assumptions. Their final totals must match.

### 12.4 Physical versus financial curves

Physical progress may use normalized item weights, quantities, labor-hours, or weighted milestones. Financial progress uses cost or billing amounts. The interface must never label one as the other.

## 13. Earned value management

At the status date:

- `PV`: budgeted value of work scheduled
- `EV`: budgeted value of work performed
- `AC`: actual cost of work performed
- `BAC`: total approved baseline budget

Core metrics:

`SV = EV - PV`

`CV = EV - AC`

`SPI = EV / PV`

`CPI = EV / AC`

`Percent planned = PV / BAC`

`Percent complete = EV / BAC`

`Percent spent = AC / BAC`

Forecasts:

`EAC_1 = BAC / CPI`

`EAC_2 = AC + (BAC - EV)`

`EAC_3 = AC + (BAC - EV) / (CPI × SPI)`

`ETC = EAC - AC`

`VAC = BAC - EAC`

`TCPI_BAC = (BAC - EV) / (BAC - AC)`

`TCPI_EAC = (BAC - EV) / (EAC - AC)`

Every forecast must identify its formula and assumption. Ratios are undefined when the denominator is zero.

## 14. Productivity

For quantity produced `Q`, labor hours `LH`, equipment hours `EH`, labor cost `LC`, equipment cost `EC`, and elapsed working time `T`:

`Output per labor-hour = Q / LH`

`Labor-hours per unit = LH / Q`

`Output per equipment-hour = Q / EH`

`Output per working day = Q / T_days`

`Direct unit cost = (LC + EC + other direct cost) / Q`

`Utilization = Productive hours / Available hours`

`Productivity variance % = (Actual rate - Planned rate) / Planned rate`

When lower values are better, such as labor-hours per unit, the UI must reverse the interpretation rather than using a misleading generic favorable/unfavorable rule.

### 14.1 Remaining-duration forecast

For remaining quantity `Q_rem` and forecast production rate `R_forecast`:

`Forecast working duration = Q_rem / R_forecast`

The selected rate source must be stored: planned, latest shift, rolling `n` periods, weighted average, best-fit trend, or manual.

## 15. Cash flow

Planned billing may be derived from earned/planned work with contractual adjustments:

`Gross billing = Eligible completed value`

`Net billing = Gross billing - retention - advance recovery - deductions + approved adjustments`

`Expected receipt date = Billing date + payment lag under payment calendar`

Retention release, mobilization advance, taxes, and deductions must be modeled as separate lines to preserve auditability.

## 16. Resource demand

For assignment rate `u_i(t)` across activity working periods:

`Resource demand_r(t) = Σ assignments for resource r active at t`

Overallocation occurs when demand exceeds resource availability under the resource calendar. Histograms must state whether values are units, hours, crews, or cost.

## 17. Aggregation and rollups

WBS and report rollups must sum quantities only when units are compatible. Mixed-unit physical quantities must not be added. Costs and hours may be summed after currency and unit validation.

Percent rollups must be weighted, not averaged naively. Valid weighting bases include BAC, planned quantity, labor-hours, or explicit weight. The report must identify the basis.

## 18. Calculation warnings

At minimum, the engine must generate structured warnings for:

- Circular logic
- Open-ended activities
- Missing project finish
- Negative float
- Hard constraints
- Negative lag
- Out-of-sequence progress
- Actual finish before actual start
- Status date earlier than recorded actuals
- Baseline totals not reconciling
- Unallocated BOQ cost
- PERT estimate order violations
- Undefined EVM ratios
- S-curve residual above tolerance
- Resource over-allocation
- Calendar gaps or invalid shifts
- Stale calculated results after input changes

Warnings need stable codes, severity, affected entity IDs, human-readable explanation, and suggested correction.

## 19. Reference test examples

Implementation must include independently verified fixtures for:

1. A simple linear FS network
2. Branching network with two paths and free float
3. All four relationship types with positive lag
4. Negative lag warning
5. Multiple calendars and holidays
6. Hard finish constraint producing negative float
7. In-progress update with retained logic
8. PERT path probability
9. BOQ unit-price and markup waterfall
10. S-curve reconciliation across weekly periods
11. EVM metrics including undefined denominators
12. Productivity forecast from rolling averages

Expected dates and values must be committed as human-readable fixtures, not generated by the same implementation being tested.
