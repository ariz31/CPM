# Quality, Security, and Testing

## 1. Quality objective

The application will be used to make time, cost, and productivity decisions. A visually correct interface is insufficient; calculations must be reproducible, data must survive interruption and migration, and reports must reveal assumptions and warnings.

Quality gates apply to the domain engine, local persistence, project-file handling, user interface, reports, accessibility, and performance.

## 2. Definition of done

A feature is complete only when it includes:

- Accepted functional and calculation requirements
- Runtime validation and meaningful error messages
- Unit, integration, and end-to-end tests
- Offline test coverage
- Undo/redo and recovery behavior
- Data-model and migration impact assessment
- Import/export behavior
- Accessibility review
- Performance measurement for large-data paths
- User-facing documentation and sample data
- No unresolved critical or high-severity defects

## 3. Test pyramid

### 3.1 Domain unit tests

Pure, fast tests for:

- Calendar working-time arithmetic
- Relationship calculations
- Forward and backward passes
- Float and driving logic
- Constraint handling
- Baseline variance
- PERT formulas and probability lookup
- BOQ resource buildup and markup sequence
- Allocation reconciliation
- Time-phasing distributions
- S-curve accumulation
- EVM metrics and undefined cases
- Productivity rates and forecasts
- Units, decimals, and rounding

These tests must not require a browser or database.

### 3.2 Property-based tests

Useful invariants include:

- Adding then subtracting the same working duration returns the original working instant within defined boundary rules.
- CPM output respects every relationship constraint.
- `ES ≤ EF` and `LS ≤ LF` for non-negative duration.
- Final cumulative curve equals the source total within tolerance.
- BOQ allocations never create or destroy value.
- Approved baseline data is unchanged by live edits.
- Serialization then deserialization preserves authoritative values.

### 3.3 Application integration tests

Test commands, transactions, repositories, calculation invalidation, import mapping, snapshot creation, baseline creation, and report dataset generation against a real temporary IndexedDB implementation.

### 3.4 UI component tests

Focus on validation, keyboard interactions, bulk editing, stale-state indicators, warning display, and report controls rather than duplicating domain formula tests.

### 3.5 End-to-end tests

Critical workflows:

1. Create a blank project and calendar.
2. Add WBS, activities, and relationships.
3. Calculate and inspect critical path.
4. Create baseline.
5. Post progress and recalculate.
6. Add BOQ and allocate cost.
7. Generate S-curve and EVM report.
8. Export `.cpmproj`.
9. Delete local project.
10. Import exported file and verify reconciliation.
11. Repeat core steps with network disabled.

### 3.6 Visual and report regression

Use stable sample projects to compare Gantt, network, chart, and PDF outputs. Avoid fragile pixel-only comparisons where semantic checks can verify labels, dates, totals, legends, and pagination.

## 5. Calculation verification

### 5.1 Independent expected values

Expected outputs must not be generated by the implementation under test. They should come from hand calculations, published textbook examples with permissible use, or independently implemented verification scripts reviewed separately.

### 5.2 Cross-tool comparison

Where possible, compare simple supported networks with established scheduling tools. Differences must be investigated for calendar, lag, constraint, and date-boundary conventions rather than adjusted blindly.

### 5.3 Formula trace

Development builds should expose a calculation trace for selected activities and metrics. The trace includes candidate dates, driving requirement, calendar operations, and formula inputs.

## 6. Data integrity testing

Required scenarios:

- Browser/process termination during autosave
- Termination during baseline creation
- Termination during import and migration
- Storage quota exhaustion
- Duplicate and orphan references
- Database upgrade from every supported schema
- Export while calculation results are stale
- Restore over an existing project
- Attachment missing or checksum mismatch
- Very large values and decimal precision
- Project opened in another timezone/locale
- Repeated export/import cycles

No destructive replacement should occur until a complete new state is validated and committed.

## 7. Offline testing

Automated and manual testing must verify:

- First online installation caches the complete application shell.
- Previously opened projects load offline.
- New projects can be created offline.
- Schedule, BOQ, S-curve, EVM, productivity, report, import, and export functions work offline.
- No core action waits indefinitely for network.
- Fonts, icons, templates, and help needed for core use are locally available.
- App updates do not remove local projects.
- A failed update rolls back to the last usable shell where platform capabilities allow.

## 8. Security model

### 8.1 Threats in scope

- Malicious or malformed imported project files
- ZIP bombs and oversized attachments
- Path traversal inside archives
- Script or formula injection through imported text
- Spreadsheet formula injection in CSV/XLSX export
- Corrupted checksums or schema data
- Cross-project reference confusion
- Untrusted attachment rendering
- Dependency compromise
- Local data exposure on shared devices
- Future sync authentication and authorization errors

### 8.2 Import hardening

- Enforce compressed and uncompressed size limits.
- Limit entry count and nesting depth.
- Reject absolute paths and `..` traversal.
- Validate MIME type independently of file extension.
- Validate images by dimensions and decoded pixel budget.
- Parse JSON with schema and depth/size limits.
- Treat all imported text as plain text.
- Never evaluate imported expressions or HTML.
- Validate IDs and cross-references before persistence.
- Verify every declared checksum.
- Import into a new project/copy by default.

### 8.3 CSV and spreadsheet safety

On export, cells beginning with `=`, `+`, `-`, or `@` that originated as text must be escaped or safely encoded to prevent formula execution when opened in spreadsheet software. Import must treat formulas as values unless a trusted template explicitly maps them.

### 8.4 Content security

A web build should use a strict Content Security Policy, avoid unsafe inline script, restrict worker and object sources, and render user content through escaping/sanitization. Attachments should open through safe object URLs or downloads, not privileged embedded execution.

### 8.5 Local confidentiality

Offline storage is not automatically encrypted. The application must explain that browser profiles and device accounts control local access. Future optional project encryption should use established authenticated encryption and a recovery design; custom cryptography is prohibited.

### 8.6 Privacy

- No mandatory analytics.
- No remote upload without explicit action.
- Diagnostics are local and redacted by default.
- Optional telemetry, if introduced, must be opt-in and exclude project data.
- Users can export and delete all local data.

## 9. Dependency and supply-chain controls

- Use lockfiles and reproducible installs.
- Review dependency licenses.
- Enable automated vulnerability alerts.
- Pin CI actions to trusted versions or commit SHAs.
- Generate a software bill of materials for releases.
- Sign release artifacts when distribution begins.
- Avoid abandoned libraries for core calculation or storage.
- Review high-risk parsing, archive, spreadsheet, and PDF libraries carefully.

## 10. Performance testing

### Benchmarks

Measure at least:

- Project open time
- Initial activity-grid render
- CPM recalculation time
- Network layout time
- S-curve generation time
- BOQ recalculation time
- Import/export time and memory
- PDF generation time
- IndexedDB transaction latency

### Dataset sizes

- Small: 100 activities / 300 relationships
- Medium: 1,000 activities / 3,000 relationships
- Large: 5,000 activities / 15,000 relationships
- Stress: documented limits beyond supported range

Performance tests should run on representative mid-range hardware or throttled CI profiles. Results and regressions should be recorded.

### Algorithmic safeguards

- Topological schedule calculation should be approximately linear in activities plus relationships for a normal pass.
- Period aggregation must avoid rescanning all records for every output period.
- Large grids and lists require virtualization.
- Network rendering requires level of detail and selection-focused rendering.
- Workers must support cancellation and stale-result rejection.
- Imports should stream or chunk where feasible.

## 11. Accessibility testing

- Automated accessibility checks on core pages
- Keyboard-only completion of critical workflows
- Screen-reader checks for grids, dialogs, metrics, and warnings
- 200% zoom and reflow tests
- High-contrast and color-vision checks
- Touch-target checks on tablet/mobile layouts
- Accessible alternative for Gantt, network, and chart data

Accessibility defects affecting project creation, activity editing, calculation, progress updates, or export block release.

## 12. Browser and platform matrix

Initial support should prioritize current stable Chromium, Firefox, and Safari where required APIs are available, with documented differences for file-system access. PWA installation behavior should be tested on Windows, macOS, Linux, Android, and iPadOS where practical.

A fallback download/upload file workflow is required when direct file handles are unavailable.

## 13. Release gates

### Pre-merge

- Type checking
- Linting and formatting
- Domain unit tests
- Relevant integration tests
- Migration tests for schema changes
- No new high-severity security finding

### Main branch

- Full test suite
- Build and offline smoke test
- Fixture reconciliation
- End-to-end critical path
- Bundle-size and performance regression checks

### Release candidate

- Full supported-browser matrix
- Import/export round-trip
- Upgrade from prior release
- Offline installation and startup
- PDF/report review
- Accessibility review
- Security review of parsers and file changes
- Backup/recovery drill

## 14. Defect severity

- **P0/Critical:** data loss, corrupted project, incorrect authoritative calculation without warning, security compromise, app cannot open projects
- **P1/High:** major workflow unusable, serious report error, baseline or file incompatibility, recurring crash
- **P2/Medium:** workaround exists, localized incorrect behavior, important accessibility defect
- **P3/Low:** cosmetic or minor usability issue without data/calculation impact

P0 and P1 defects block production release.

## 15. Error handling requirements

Errors need stable codes and should state:

- What failed
- Whether data remains safe
- What the user can do next
- Whether retry is safe
- Whether a recovery copy or diagnostic export is available

Raw stack traces should remain in diagnostics rather than primary user messages.

## 16. Backup and recovery verification

At least one automated or manual release test must:

1. Create a representative project.
2. Create a baseline and progress update.
3. Export a full `.cpmproj` file.
4. Corrupt the working local database or remove the project.
5. Import the file.
6. Verify entity counts, key schedule dates, BAC, curve totals, and attachment hashes.

## 17. Documentation quality

Requirements, formulas, architecture, schema, workflows, and release notes are version-controlled product assets. Pull requests that alter behavior must update the relevant documentation and fixture expectations in the same change.
